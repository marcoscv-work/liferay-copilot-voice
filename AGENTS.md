# Liferay Copilot Voice — Codex working guide

## Project overview
Voice-driven content creation copilot for Liferay CMS. Plain HTML + CSS + JS, no build step. Target: publish on marketplace.liferay.com as a **custom element client extension** under a personal App Publisher account.

Two runtimes from one codebase, both booting through the `<liferay-copilot-voice>` custom element (`element.js`):

- **Standalone** (dev): `npm start` — dev-server proxy + session-cookie auth against any Liferay instance.
- **Portal** (production): `npm run package` → source client extension zip. Same-origin `fetch` + `Liferay.authToken`, locale from `Liferay.ThemeDisplay`, dev surfaces hidden. Detection: `inLiferayPortal()` in `src/02-liferay.js`.

The architecture is **data-driven**: commands, labels, steps and step structure come from `flows.{lang}.json`; UI + screen-reader strings from `language/Language_{lang}.properties`; runtime settings from `config.json`. the `src/` modules own the engine (animation, speech, dispatch, modals, format pass, Liferay API layer).

## Run it

```bash
npm install       # one-time
npm start         # http://localhost:8765 (dev server + proxy)
npm run package   # dist/liferay-copilot-voice.zip (source client extension)
```

Needs a browser with the Web Speech API + AudioContext — Chrome, Edge or Safari (Firefox does not ship SpeechRecognition yet). The code detects the capability generically, never the browser.

## Boot sequence

Both runtimes: `<liferay-copilot-voice>` connected → `element.js` renders the markup from `markup.js` into the element's light DOM (adds `.copilot-voice-root`, plus `.in-portal` when `Liferay.ThemeDisplay` exists), sets `window.__copilotVoiceBaseURL` from its own script src, then appends the eight `src/*.js` modules in order (async=false). The runtime then does:

```
1. setBarsOval()                     instant DOM reset
2. loadAll()  → resolveLocale() (portal: ThemeDisplay wins; standalone: localStorage), then Promise.all of:
     loadJSON(`${ASSET_BASE}config.json`, DEFAULT_CONFIG)
     loadProperties(`${ASSET_BASE}language/Language_${lang}.properties`)
     loadJSON(`${ASSET_BASE}flows.${lang}.json`, null)
3. applyConfig()                     keycap label + applyStrings() over [data-language]
4. buildCmdList()                    cmd-list <ul> from flowsConfig.globalCommands
5. renderSidePanel()                 side-panel <ul>, contextual to voicePhase
6. paintLocaleToggle(lang)           highlight active locale in .language-toggle
7. applyLiveDebug(persisted)         restore .debug-live-regions if previously enabled
8. preloadLiferaySpaces()            fire-and-forget Liferay site preload → discoverDynamicFlows()
```

`ASSET_BASE = window.__copilotVoiceBaseURL || './'` — inside the portal assets resolve against the client extension's static dir, not the page URL. If either JSON fails the prototype still loads with defaults. `flowsConfig === null` short-circuits `handleFlowCommand` and the global-command matcher.

## Portal runtime — custom element client extension

- `inLiferayPortal()` (src/02-liferay.js) = `Liferay` global with `ThemeDisplay` present. Single detection point; never sniff anything else.
- **Auth**: `lrFetch` and `postFile` go same-origin (`base = ''`) with header `x-csrf-token: Liferay.authToken`. No Basic auth, no proxy. Standalone keeps the dev-server proxy path.
- **Locale**: `resolveLocale()` portal priority is `?lang` → ThemeDisplay (BCP47 or `es_ES`-style) → navigator. The full portal BCP-47 tag is used for STT when its prefix matches. `lang` attr lands on the element; `documentElement.lang` only touched standalone.
- **Hidden in portal** (CSS via `.in-portal`): `.language-toggle`, `.dev-toggle`, the banner's `/config` link.
- **Assist**: `ensureAssist()` refuses relative endpoints in portal (the dev `/assist/review` route doesn't exist there) → deterministic format pass unless an absolute endpoint is configured.
- **CSS scoping**: every rule lives under the element; the reset is `liferay-copilot-voice, liferay-copilot-voice * {…}`. Design tokens `--cv-brand/-strong/-soft, --cv-text/-muted/-faint, --cv-border, --cv-neutral, --cv-bg, --cv-danger` are defined on the element and used as `var(--cv-x, #literal)` everywhere — a portal theme can re-map them with a tiny CSS override.
- **Packaging**: `npm run package` copies runtime files into `client-extension/liferay-copilot-voice/assets/`, zips the folder (source CX → `dist/liferay-copilot-voice.zip`) and mirrors it into `liferay-workspace/client-extensions/` (generated copy — never edit it). `npm run build:cx` then runs the workspace `gradlew assemble` and copies the **deployable** zip to `dist/liferay-copilot-voice-deployable.zip` (LUFFA format: generated `*.client-extension-config.json` + `static/` + `WEB-INF/`; assets served at `${portalURL}/o/liferay-copilot-voice/`). Set `LIFERAY_HOME` to also drop it into the bundle's `deploy/`. The `liferay-workspace/` (blade-inited, product `portal-7.4-ga132`, workspace plugin 12.1.11) is committed; its `client-extensions/`, `.gradle/`, `build/`, `bundles/` are gitignored. `client-extension.yaml`: `type: customElement`, `htmlElementName: liferay-copilot-voice`, `urls: [markup.js, element.js]` (order matters; the src/*.js modules are loaded by element.js), `cssURLs: [styles.css]`, `instanceable: false`.
- **Security invariants (audit P0-2)**: any text from Liferay (names, labels, picklist values) or from dictation reaches the DOM via `textContent` or `escapeHTML()`; image URLs pass `safeImageURL()` (http/https only, CSS-quoted) before any `background-image`. `innerHTML` is reserved for static audited templates (marked with an "Audited template" comment). A lint test in test/security.test.js fails the build on new unescaped interpolations near HTML sinks, and scripts/css-scope.js keeps every stylesheet selector anchored to the element.
- **A11y invariants (audit P1-1..P1-4)**: `setUiMode` drives `inert` alongside `.visible` — hidden overlays are out of the a11y tree and Tab order; during `modal: true` modes everything except the dialog (MODAL_SURFACE_IDS) is inert, which IS the focus trap; focus moves to `focusTarget` on open and returns on close; Escape dismisses (submitConfirm has a third path, `dismissAiConfirm()`, because answering "no" SUBMITS). The keycap and all picker cards are real `<button>`s with `aria-pressed`. Anything shown outside setUiMode (e.g. showCommandList) must manage its own `inert`.
- **markup.js** is the only markup source. When changing markup, edit `markup.js` (index.html no longer carries the stage markup).

## Architecture — runtime modules (src/)

### Activation

- **Single press toggle**: one keypress activates listening, another stops it. From idle → toPressed → toMorph → toListening. From listening → toIdle (force-reset).
- Key from `config.json` via `appConfig.activationKey.code`. Fallback `Space`.
- **Two-press cancel during flow**: pressing the activation key while in a flow phase (`voicePhase !== 'command'`) shows the `.cancel-confirm` pill ("Pulsa SPACE otra vez para cancelar"). Second press within 5 s actually cancels. Auto-dismiss after 5 s, or on any voice command match. Doesn't apply when `voicePhase === 'command'` (idle listening) — there a single press toggles directly.
- Touch: `touchstart` runs the same `activationToggle()` only when target is **not** inside an interactive zone (selector list `TOUCH_INTERACTIVE`).

### Animation states (`appState`)

```
idle → pressed → morphing → listening ⇄ speaking
```

All transitions go through: `toIdle()`, `toPressed()`, `toMorph()`, `toListening()`, `toSpeaking()`, `toStopSpeaking()`. `toMorph`'s deferred actions (rAF + barsTimer) bail if `appState !== 'morphing'`, so a fast SPACE→SPACE during morphing leaves no residue.

### Voice phases (`voicePhase`)

```
'command'         listening for global commands (crear contenido, ayuda, comandos, salir, …)
'space'           picking a Liferay space (only cancel honoured)
'title'           dictating title (append-on-return)
'subtitle'        dictating subtitle (append-on-return)
'body'            dictating body  (append-on-return)
'dynamicText'     dictating into a 3rd+ Text field (dynamic Object flows only)
'options'         Picklist / Boolean options picker — cancel + volver honoured; selection via matchOptionFromVoice
'numberInput'     numeric input panel — Integer / Long / Double / BigDecimal / Decimal fields
'dateInput'       date/datetime panel — part-by-part or full-date voice + native keyboard input
'image'           cover image picker
'file'            file picker (createFile flow)
'submitConfirm'   "¿revisar formato?" Sí/No
'aiLoading'       3 s mock spinner
'aiReview'        format-reviewed content with Aceptar / Cancelar
'formatList'      "Comandos de formato" overlay (only "volver" honoured to dismiss)
```

Side panel commands and accepted voice phrases are **contextual to the current phase** (see `getActiveCommands()` and step-level `flowCommands`).

### Flow session token (race-safe deferred actions)

Every flow-related deferred action goes through:

```js
let flowSessionId = 0;
function newFlowSession() { flowSessionId++; }
function flowTimeout(fn, ms) {
  const sid = flowSessionId;
  return setTimeout(() => { if (sid === flowSessionId) fn(); }, ms);
}
```

`newFlowSession()` is bumped at the start of `toIdle`, `cancelFlow`, `finalizeSubmit`. Any pending `flowTimeout` scheduled before the bump is silently dropped. Plus `toIdle` runs a final defensive cleanup pass: clears `keycapWrap` transform, removes `.visible` from every flow overlay, hides `formError` and the cancel-confirm pill, resets the file picker selection state and the inline carousel-track styles.

### bar3 = mic oval

- bar3 starts as the mic body (48×80 blue pill at `top:119px`).
- On activation: springs to bar shape (20×38) via BOUNCE cubic-bezier.
- bars 1,2,4,5 start at `width:0`, expand on transition.
- **CSS spring append pattern**: `barEls[2].style.transition += ', background 0.4s ease'` — never replace the transition string mid-spring or it snaps to end value.

### RAF bar animation

- **Purple phase** (`now < commandBoostUntil`): fixed heights `[72, 88, 100, 88, 72]`, no audio reactivity.
- **Audio-driven** (AudioContext running): FFT bins → 5 bands → exponential smoothing.
- **Sine fallback**: when mic unavailable.
- Spring formula: `liveH[i] += (target - liveH[i]) * (1 - Math.exp(-k * dt))`.

### Audio sensitivity

Two thresholds (top-of-file constants in `src/01-core.js`) govern visual reactivity. **Neither affects recognition** — Web Speech API has its own VAD.

```js
const SPEECH_THRESHOLD = 62;  // out of 255 — energy above this flips bars to active mode
const NOISE_GATE       = 56;  // out of 255 — bars ignore audio energy below this for visual reactivity
```

Bump up if bars react to ambient noise; bump down if they don't react to real speech.

### AudioContext

- Initialised once on first activation, never destroyed.
- `pauseMic()` only clears timers — never calls `audioCtx.suspend()` (would need user gesture to resume).

### Speech recognition — provider seam

The rest of the app talks to a single `speech` object. **To swap to Deepgram / AssemblyAI / Google STT / Whisper / etc., implement a `createXProvider(opts)` returning the same shape and register it in `createSpeechProvider`.** No other file needs to change.

```js
// Contract:
provider.start()           // begin listening (idempotent)
provider.stop()            // stop listening (idempotent)
provider.setLocale(loc)    // change BCP-47 locale at runtime
provider.available         // boolean — supported in this environment
provider.name              // 'web-speech' / 'deepgram' / etc.

// Provider receives via factory opts:
opts.onResult({ interim, final })  // strings, empty when not present
opts.onEnd()                        // session ended (manual or network)
opts.onError(err)                   // optional
```

Default provider: `createWebSpeechProvider(opts)` — wraps the browser's `SpeechRecognition` and emits the unified contract. Configured via `appConfig.speech.provider`.

The phase-routing logic lives in `handleSpeechResult({ interim, final })` — provider-agnostic.

### Two sounds

`playSound(kind)`:
- `'command'`: 660→880 Hz, decisive (recognized command, submit, cancel, space picked, image picked).
- `'fieldChange'`: 520→700 Hz, softer (auto-advance title→body, `goToStep`, `clearStep`, `exitStep`, `selectFile`, image carousel toggle).

`flashCommandDetected(label, soundKind)` plays the sound + 900 ms purple flash + the bars-label pill (with check icon, label-aware: short labels stay centered, long labels right-align in corner mode).

### Active-field focus

`updateFieldFocus()` toggles `.dictating` on the current field's `.field-box` based on `voicePhase`. Adds halo (`field-glow`) and reveals `.field-mic` (`mic-pulse`). Called via `renderSidePanel()`.

### Dictation fields are real `<input>` / `<textarea>`

Title and subtitle are `<input class="field-input">`, body is `<textarea class="field-textarea">`. The user can dictate or type — both paths converge on `titleValue` / `subtitleValue` / `bodyValue`.

- `renderField(el, text, isInterim)` writes `el.value` and toggles `.field-interim` (the whole text colours light blue `#80acff` while STT is delivering tentative output).
- `bindFieldInput()` wires each input: `input` event syncs the JS state and removes interim colour; `Enter` on title/subtitle advances to the next phase; body textarea inserts a newline on Enter as expected.
- `handleSpeechResult` skips writing to a field that has real focus (`fieldIsFocused()`) — manual edits win when the user is typing.
- The global `keydown` listener for the activation key skips when `e.target.tagName === 'INPUT' || 'TEXTAREA'` so SPACE inside a field types a space instead of toggling voice.
- Native browser caret + native `placeholder` (driven by `data-i18n-placeholder` keys `placeholderTitle`/`placeholderSubtitle`/`placeholderContent`). Old `.field-text`/`.field-placeholder`/`.field-cursor` classes are gone.

### Speech residual drain

When the matcher fires on an interim (space picker via `spaceMatchOnInterim`, `ackCommand` for help/exit), the rest of the same utterance is still streaming. Two flags coordinate the drain:

- `skipNextFinal` — drops the next `final` event entirely.
- `dropResidualInterims` — drops `interim` events until the next `final` clears both flags.

`handleSpeechResult` checks them at the top before any phase routing. Without both, residual interims after a mode transition would land in the next phase's input (e.g. "crear contenido marketing" said in one breath would type "crear contenido marketing" as the title after the 950 ms transition into `flow:title`).

`resetContentFlow()` resets both flags to `false`. The exit branch in the global command matcher reapplies them *after* `toIdle()` so the residual final of "salir" still gets caught.

### Don't write captured speech into a backgrounded field

**Criterion:** the recogniser stays running everywhere (voice commands keep working in pickers and modals) — we never *suspend capture*. What we gate is *writing*: speech captured while a dictation field is in the background (behind the space picker, the review modal, etc.) must not be written into that field.

- `utteranceInFlight` — a live mirror of the recogniser, set `true` on a bare `interim` and `false` on each `final`. It answers "is the user mid-utterance right now?".
- `setUiMode` is the single chokepoint: when the new phase is a dictation phase (`isDictationPhase` = `title`/`subtitle`/`body`/`dynamicText`) **and the previous phase was not**, and `utteranceInFlight` is `true`, it arms the drain (`skipNextFinal` + `dropResidualInterims`). So whatever was being said while the field was backgrounded is dropped; a fresh utterance started once the field is foreground is kept. This covers both space→title and modal→body (e.g. talking through "revisar formato").
- Do **not** reach for stopping the recogniser or a time-window heuristic — those were tried and reverted. The in-flight check is exact: it drops only the straddling utterance, and cumulative interims mean nothing is lost when the drain releases.

### Field-mic mute commits in-flight text

`setFieldMicMuted(true)` (the per-field "Pausar entrada de voz" button) calls `commitActiveDictationField()` first: it promotes the tentative (blue, `.field-interim`) text showing in the active field into the backing state (`titleValue` / `subtitleValue` / `bodyValue` / `dynamicFieldValues[stepId]`) and removes the interim colour. Pausing therefore *freezes* what's on screen as final/black immediately — no waiting for a keypress or a trailing `final`.

### Sounds

Three tones, jerarquized by importance, all generated in-engine via `playSound(kind)` with `AudioContext`:

| `kind` | Frequencies | Total dur | Use |
|---|---|---|---|
| `command` | 660 → 880 Hz, two tones | ~300 ms | Actions that change content state — open flow, select space/image/file, send, cancel, modal answers. |
| `fieldChange` | 520 → 700 Hz, two tones (softer) | ~170 ms | Field navigation — `goToStep`, `clearStep`, `exitStep`, `selectFile`, `deleteLastWord`, automatic title→body advance. |
| `ack` | 880 Hz single tone (low vol) | ~70 ms | "I heard you" for low-priority meta-commands. Today: `ayuda` and `salir`. Fired by `ackCommand()` which also sets the matcher dedup flags. |

`flashCommandDetected(label, kind)` plays the sound + sets `commandBoostUntil` + flashes the bars purple + shows the bars-label pill. The dispatcher consults two sets:

- `FIELD_CHANGE_ACTIONS` — picks the softer `'fieldChange'` tone instead of `'command'`.
- `NO_FLASH_ACTIONS = {'submit'}` — plays the sound without the visual flash. `submit` qualifies because the keycap returning to centre + prominent "Enviado" already telegraphs the action; the flash visually collided with the bars settling.

### Format pass (bilingual ES + EN)

Used by the "Revisar formato" review step (was "Revisar con IA"). All deterministic and idempotent — no LLM.

1. **Inline punctuation** (`applyInlinePunctuation`): spoken words become glyphs.
   - `punto y coma` / `semicolon` → `;`
   - `dos puntos` / `colon` → `:`
   - `interrogación` / `question mark` → `?`
   - `exclamación` / `exclamation mark|point` → `!`
   - `abrir interrogación` → `¿`, `abrir exclamación` → `¡`
   - `coma` / `comma` → `,`
   - `punto final` / `punto` / `period` / `full stop` → `.`
2. Trim + collapse whitespace.
3. Capitalize first letter (skips leading `¿ ¡ " '`).
4. Capitalize after sentence-ending punctuation.
5. Insert comma before transitional connectors: `pero/aunque/sin embargo/por (lo) tanto/porque + but/although/however/therefore/because`.
6. **Question wrap**: if text starts with a question word/auxiliary (`qué/cómo/dónde/cuándo/por qué/cuál/quién/cuánto + what/how/where/when/why/which/who/whom/whose/do/does/did/can/could/would/should/will/won't/is/are/am/was/were/has/have/had/may/might/must`), wrap with `¿…?` (es-locale) or `…?` (otherwise).
7. Otherwise add final period if no terminal punctuation.

Title doesn't get a final period (only the question wrap if applicable).

### AI/Format review modal — two paths

- **Submit flow** (`enviar` → `¿Quieres revisar el formato?` → `sí`): `startAiReview(true)`. Modal accept button reads `aiReviewAccept` ("Aceptar y enviar"). On accept, replaces `titleValue` / `bodyValue` with formatted versions and calls `finalizeSubmit`.
- **Direct command** (`revisar formato`): `startAiReview(false)`. Modal accept button reads `aiReviewAcceptOnly` ("Aceptar"). On accept, replaces values, returns to body step (no submit). Cancel returns without applying.

Internal flag `aiReviewAcceptSubmits` switches behaviour. The modal command labels in `flows.json modalCommands.aiReview` are kept neutral ("Aceptar" / "Cancelar"); the modal *button* text is set dynamically based on the path.

### Gemini writing assist (optional, configurable)

The format-review step can optionally run a real LLM (Gemini) instead of the built-in deterministic format pass, to genuinely improve the wording. It is **purely additive**: with nothing configured the prototype behaves exactly as before, and any failure falls back to the deterministic pass — so it can never block a submit.

**Client seam (`assist`)** — a sibling of the `speech` and `api` seams, deliberately separate so the rest of the app is untouched:

```js
assist.review({ title, subtitle, body }) → Promise<{ title, subtitle, body }>
assist.available / assist.name
```

- `createAssistProvider(name, opts)` returns `null` for `'none'`/absent (→ deterministic path) or `createGeminiAssistProvider(opts)` for `'gemini'`.
- `ensureAssist()` lazily builds it from `appConfig.assist` (`{ provider, model, endpoint }`).
- `startAiReview` branches **clearly**: `assist?.review` present → `runGeminiReview()` (real network call, guarded by `flowSessionId`, falls back to `deterministicReview()` on any error); absent → the deterministic `formatAsTitle`/`formatAsBody` pass wrapped in a 500 ms anti-flash delay. Both render through the shared `showAiReviewResult({title,subtitle,body})`.
- The loading modal shows which reviewer is running: `#aiLoadingModel` → `Modelo: {model}` (Gemini) or `Formato local (sin IA)` (deterministic). Strings `aiLoadingModel` / `aiLoadingModelLocal`.

**Server side (dev only)** — Gemini is never called from the browser; the key never reaches it. `dev-server.js` exposes `POST /assist/review` (boxed `DEV-ONLY GEMINI ASSIST` block) which calls Gemini `generateContent` with a structured-output schema (`{title,subtitle,body}`) and a conservative prompt ("improve wording, don't change meaning, don't translate, respect the locale"). Returns non-2xx when no key is set, so the client falls back. In production this route is replaced by a host-provided endpoint; the `assist` seam contract is unchanged.

**Enabling it** — two parts:
1. `config.json` → `"assist": { "provider": "gemini", "model": "gemini-flash-latest", "endpoint": "/assist/review" }`. `provider: "none"` (or absent) disables it. The model defaults to `gemini-flash-latest` (a robust alias — a specific id like `gemini-3.1-flash` may 404 depending on the project).
2. The API key, server-side only: env `GEMINI_API_KEY`/`GOOGLE_API_KEY` (wins), **or** the `/config` page's "Gemini writing assist" card → `POST /api/dev-assist` persists it to `dev-config.local.json` (gitignored). The card masks an existing key (`••••••••`), clears on focus, and never re-sends the mask (an untouched field keeps the saved key). Model override there beats `config.json`.

### Multi-flow

`currentFlowId` tracks which flow is active. `getFlow()` returns `flowsConfig.flows[currentFlowId]`. Flows currently registered:

```
createWebContent  → submitApi: submitWebContent     (steps: space → title → body → coverImage)
createBlog        → submitApi: submitBlog           (same shape, different labels/voicePrompts)
createFile        → submitApi: uploadFile           (steps: space → file)
```

`submitFlow()` in dispatch consults `flow.submitApi` and routes to the right helper:
- Content / Blog → `submitContent()` (validate title+body → AI confirm → finalize)
- File → `submitFile()` (validate selectedFile → finalize, **skips AI confirm**)

`finalizeSubmit()` calls `api[flow.submitApi]({ spaceId, title, content, coverImageId, file })` — single payload shape, the seam picks what it cares about.

### File step

- `voicePhase === 'file'` shows `.file-picker` (centered card with prompt, button, info row).
- `<input type="file" hidden>` triggered by:
  - Click on the visible button.
  - Voice command "elegir archivo" / "seleccionar archivo" / "escoger archivo" / "abrir archivo" → action `selectFile` → `openFileDialog()`.
- **Browser limitation**: `<input type=file>.click()` requires a *trusted* user gesture; Web Speech events don't qualify, so the dialog often won't open from voice. We always pulse the button (`.file-picker-btn.flash` 1.5 s) so the user knows to click it manually.
- File selection wires through `setSelectedFile(file)` → updates `selectedFile`, displays name + formatted size, marks the card `.has-file`.
- `submitFile()` validates `selectedFile` (inline `formError` if missing) and goes straight to `finalizeSubmit()`.

### Two-press cancel pill

- Element: `.cancel-confirm` (id `cancelConfirm`, role="alert", `hidden` by default).
- Triggered when activation key pressed mid-flow. Shows `s('cancelConfirm')` template.
- Auto-dismiss `CANCEL_CONFIRM_MS = 5000`. Also dismissed by any successful voice command match (in `handleFlowCommand`).

### Accessibility — screen reader announcements

The prototype is designed to be usable by a blind user with a screen reader running. Every visible UI surface mirrors through one primitive: `announce(text, level)`.

**Live regions** — two SR-only `<div>`s in `index.html`, inside `.stage`:

```html
<div id="liveStatus" role="status" aria-live="polite"    aria-atomic="true" class="sr-only"></div>
<div id="liveAlert"  role="alert"  aria-live="assertive" aria-atomic="true" class="sr-only"></div>
```

`.sr-only` is a standard utility (`position: absolute; width: 1px; height: 1px; clip: rect(0,0,0,0); …`) that keeps the element in the accessibility tree without painting it.

**API**:

```js
announce(text)             // → liveStatus  (polite, queued, doesn't interrupt)
announce(text, 'alert')    // → liveAlert   (assertive, interrupts current speech)
```

Implementation does a `clear-then-set` on the next animation frame so screen readers re-announce identical text instead of skipping it.

**Mode-level announcements (declarative)**:

Each entry in `MODES` declares an `announce` field. Three shapes:

```js
announce: { stringKey: 'announceListening' }   // → s('announceListening')
announce: { stepRef: 'title' }                  // → getStep('title').voicePrompt
announce: { fn: 'aiReviewSummary' }             // → ANNOUNCE_BUILDERS[fn]()
announce: null                                   // silent
```

`setUiMode` resolves the descriptor and only fires when `prevMode !== mode` (no repetition on re-renders).

**Dynamic builders** — `ANNOUNCE_BUILDERS` registry. Each function returns the string to announce. Today:

| Builder | Used by | What it composes |
|---|---|---|
| `flowSpacePrompt` | `flow:space` | step prompt + list of space names + cancel hint |
| `flowImagePrompt` | `flow:image` | step prompt + list of image names + back hint |
| `aiReviewSummary` | `flow:ai-review` | tag + reviewed title/subtitle/body + actions hint |
| `helpCommandList` | `showCommandList()` | title + global command labels |

Convention for pickers/modals: **prompt → suggestion (options) → actions**. Use the `joinAnnounce(...)` helper to compose with `". "` separators and skip empties.

**Event-level announcements (imperative)**:

| Event | Where | Level |
|---|---|---|
| Final transcript in title/subtitle/body | `handleSpeechResult` | status |
| `selectSpace` | `selectSpace()` | status |
| `selectCoverImage` | `selectCoverImage()` | status |
| `setSelectedFile` | `setSelectedFile()` | status |
| `clearTitle` / `clearSubtitle` / `clearBodyContent` | each function | status |
| `clearCoverImage` | `clearCoverImage()` | status |
| `deleteLastWord` | `deleteLastWord()` | status |
| `showFormError` | `showFormError()` | **alert** |
| `showCancelConfirm` | `showCancelConfirm()` (HTML stripped) | **alert** |
| Mic permission denied / mic error | `initMic()` catch | **alert** |
| Speech recognition error (filtered) | `createSpeechProvider` `onError` | **alert** |

`no-speech` and `aborted` SpeechRecognition errors are intentionally NOT announced — they're normal idle/restart noise.

**Strings convention**: any SR-specific string lives under `config.{lang}.json` `strings` with prefix `announce*`. Templates accept `{name}`, `{field}`, `{list}` placeholders.

**Adding a new accessible surface**:

1. **New mode** → declare `announce` in MODES. If you need composed text (prompt + options + actions), add a builder in `ANNOUNCE_BUILDERS` and reference it via `announce: { fn: '…' }`.
2. **New step in a flow** → its `voicePrompt` in `flows.json` is the SR text. Make it a complete autocontained sentence.
3. **New error / alert** → call `announce(text, 'alert')` next to the visual error.
4. **New picker/modal** → follow the prompt → suggestion → actions pattern in a builder.

Forgetting `announce` produces silence — a deliberate fail-loud signal during a11y review.

Bottom-right corner has a `.dev-toggle` (mirror of `.lang-toggle` on the left). Hidden by default, fades in on cursor approach. The corner is reserved for dev / debug switches.

## Dynamic Object-driven flows

`buildFlowFromObjectDefinition(def, tpl)` converts a Liferay **Object Definition** (fetched from the `L_CMS_CONTENT_STRUCTURES` Asset Library folder) into a fully typed voice flow. Each Object field maps to a step type:

| Liferay `businessType` | Step type | Voice / UI |
|---|---|---|
| `Text` / `String` (1st field) | `title` | Text input — dictation appends on each utterance |
| `Text` / `String` (2nd field) | `subtitle` | Text input |
| `Text` / `String` (3rd+ fields) | `text:{fieldName}` | Injected input in `#dynamicTextFields`; `voicePhase='dynamicText'` |
| `LongText` / `RichText` | `content` | Textarea — dictation appends |
| `Picklist` | `options:{fieldName}` | Options picker — Liferay Picklist values fetched from `listTypeDefinitionId` |
| `Boolean` | `options:{fieldName}` | Options picker — synthesized `[Sí, No]` options; submits as JS boolean `true`/`false` |
| `Integer` / `Long` | `number:{fieldName}` | Number input panel — `input.step = 1`; voice parses digits and number words |
| `Double` / `BigDecimal` / `Decimal` | `number:{fieldName}` | Number input panel — `input.step = any`; voice parses decimals |
| `Date` | `date:{fieldName}` | Date input panel — `input.type = date`; value stored as `YYYY-MM-DD` |
| `DateTime` | `date:{fieldName}` | Date input panel — `input.type = datetime-local`; value stored as `YYYY-MM-DDThh:mm` |

### Date voice input — part-by-part

Because saying a full date in one breath is hard, the date panel accepts components in any order across separate utterances:

1. Say the **day** (`quince`, `15`, `día 7`)
2. Say the **month** (`mayo`, `diciembre`, `mes 3`, `march`)
3. Say the **year** (`dos mil veinticinco`, `2025`, `año 1982`)

The hint below the input tracks progress: `Día: 15  ·  Mes: may  ·  Año: —`. When all three are collected the date is confirmed automatically. A full date in a single utterance (`15 de mayo de 2025`, `hoy`, `mañana`) also works and is preferred.

### `finalizeSubmit` type coercion

Before posting to the Liferay API, `finalizeSubmit` coerces dynamic field values:

```js
Boolean  → JS boolean  true / false  (not the string "true")
Number   → Number(v)   NaN values skipped
DateTime → appends ':00' when string is 16 chars (missing seconds)
```

### `volver` in picker/input panels

`getActiveCommands()` injects a synthetic `go-back` command when the current step has a predecessor in the flow. Phrases: `volver`, `back`, `anterior`, `torna`, `go back`. Available in `options`, `numberInput`, and `dateInput` phases.

### Field conventions

- `phrases` — canonical phrases. First entry is shown in the cmd-list (capitalized via `capitalize()`). All matched as substrings after `normalize()`.
- `aliases` — additional matchable phrases not surfaced in UI.
- `hidden: true` — keep the command active but don't render it in lists.
- `style: "danger"` — render the side-panel pill in red.
- `action` + `params` — wired in `dispatchFlowAction()` (extend there for new actions).
- A step can have its own `flowCommands` and `voiceHelp` (image step does — overrides flow-level commands while in that phase).

### Locale resolution

`SUPPORTED_LOCALES = ['en', 'es', 'it']` (first entry is the fallback default). `resolveLocale()` priority:

3. Standalone only: `localStorage.lang` (user preference set by the toggle)

5. Fallback to `SUPPORTED_LOCALES[0]`

Toggle button persists choice with `setLocaleAndReload()` which strips `?lang` from the URL and reloads.

## Liferay integration

Wired against a real Liferay instance via the `api` object in `src/02-liferay.js`. The dev-server (`dev-server.js`) acts as a same-origin proxy + session-cookie holder so the browser never has to deal with CORS, cookies or sending Authorization headers itself.

### dev-server.js — proxy + session-cookie auth

```js
const TARGET = process.env.LIFERAY_URL || 'http://localhost:8080';
const PROXY_PREFIXES = ['/o/', '/c/', '/documents/', '/api/'];
```

- Anything matching `PROXY_PREFIXES` is forwarded to `TARGET` as-is.
- On startup the server **logs into Liferay** via `POST /c/portal/login` with the credentials from `dev-config.local.json` (gitignored; edited via the `/config` page) — defaulting to the stock local-bundle admin `test@liferay.com`/`test` so a fresh clone works against a vanilla `localhost:8080` with zero setup — and caches every `Set-Cookie` value (JSESSIONID, COMPANY_ID, ID, COOKIE_SUPPORT, GUEST_LANGUAGE_ID).
- On every proxied request it **rewrites the `Cookie` header** to use those cached cookies (browser cookies for Liferay names get stripped first). Liferay then processes everything as an authenticated session — including `/documents/*`.
- Basic auth is also injected as a fallback when the browser didn't send one — works for `/o/*` and `/api/*` paths even if the cookie auth ever fails.
- If a proxied response is `302 → /c/portal/login`, the session expired (Liferay default 30 min idle); the proxy fires a re-login in the background. The current request fails; the next succeeds.

### Auth code is intentionally isolated

All credential reading, login flow, cookie cache, and Cookie/Authorization header rewriting lives between two banners in `dev-server.js`:

```
╔═══ DEV-ONLY LIFERAY AUTH ═══╗
   readLiferayDevCreds()
   liferayDevLogin()
   applyLiferayDevAuth(headers)        ← single integration point
   isLiferayDevSessionExpiry(response)
╚═════════════════════════════╝
```

The `proxy()` function only references this block via `applyLiferayDevAuth(headers)`. Logs from this block are tagged `[liferay-dev-auth]` so they're easy to spot in the console.

The boxed visual + `liferayDev*` prefix + dedicated tag exist precisely so a colleague reading the file doesn't mistake any of this for a production pattern. **None of it ships.** Hardcoded credentials, login automation, and cookie rewriting are dev-time scaffolding to bridge a localhost prototype to a real Liferay backend during integration work.

### Production transition — DONE (portal mode)

The portal path is implemented — see *Portal runtime — custom element client extension* near the top. `inLiferayPortal()` switches `lrFetch`/`postFile` to same-origin + `x-csrf-token`, disables the Basic-auth path, hides dev surfaces, and `ensureAssist()` refuses the dev-only relative assist endpoint. The dev-server, its auth block and the `/config` page remain **dev-only** and are excluded from the client extension package (only the files listed in `scripts/package-client-extension.js` ship).

Still shared between both modes: the `api` object contract, the structured error contract (`err.kind === 'network' | 'server'`), the `liferayHealthy` gate (in the portal a failing preload means a permissions/config problem worth surfacing), and all accessibility wiring.

### Why session cookie auth (not just Basic)

In default Liferay DXP setups the `BasicAuthHeaderAutoLogin` filter only runs for a subset of paths — typically `/o/*`, `/api/*`, `/c/*`. **`/documents/*` is NOT covered**, so even when the proxy injects `Authorization: Basic`, Liferay ignores it for binary downloads, processes the request as Guest, and `<img src="/documents/...">` returns a 404 portal page (~85 KB HTML "Page not found").

The session cookie path bypasses this: once Liferay creates an authenticated session via `/c/portal/login`, every subsequent request with that JSESSIONID is treated as the authenticated user, including `/documents/*`. No portal config changes needed.

### Why same-origin matters for images

Independent of the auth flavor: `<img>` cross-origin to Liferay still wouldn't authenticate even if you HAD a session cookie — browsers strip cookies on cross-site subresource requests under `SameSite=Lax` (Tomcat default). Same-origin via the proxy is the only path that combines (1) authenticated server-side request and (2) browser-friendly URL. `fetchImagesForSpace` therefore returns **path-only** URLs (`pathOnly(file.fileURL || file.link?.href)`).

### Endpoints in use

| Concern | Endpoint | Notes |
|---|---|---|
| Spaces | `GET /o/headless-asset-library/v1.0/asset-libraries?pageSize=50` | We use `siteId` (not `id`) as the scope id everywhere. `settings.logoColor` is a Lexicon `outline-N` class passed through to CSS verbatim |
| Images | `GET /o/cms/basic-documents/scopes/{siteId}?pageSize=50` | Filter to `image/*` mimeTypes. Each item has `id` (basic-document Object Entry id) and `file.id` (DLFileEntry id) |
| Web content | `POST /o/cms/basic-web-contents/scopes/{siteId}` | Body `{ title, content }`. Content goes in `content`, not `contentRawText`. The Object has no native `coverImage` field — when the user picks one from the carousel we embed `<p><img src="${url}" alt="${name}"></p>` at the top of the HTML content (matches CKEditor's inline-image shape). The dictation body is HTML-escaped + wrapped in `<p>`, with `\n` runs converted to `<br>` |
| Blog | `POST /o/cms/blogs/scopes/{siteId}` | Body `{ title, subtitle, content, coverImage? }`. **`coverImage` is the DLFileEntry id as a raw `Long`** (i.e. `Number(file.id)`), NOT the basic-document Object Entry id (`d.id`). Confirmed empirically — see "CoverImage gotcha" below |
| File | `POST /o/cms/basic-documents/scopes/{siteId}` | `multipart/form-data` with `file` + `title` parts. Don't set `Content-Type` — the browser must set the boundary |

All of these are L_CMS_* Liferay Objects; if your instance has different Object definitions the field names will differ.

### CoverImage gotcha (blog)

The `coverImage` field of `CMSBlog` is an Attachment field with:
- `DBType: "Long"`, `type: "Long"`, `businessType: "Attachment"`
- `objectFieldSettings.fileSource: "userComputerToCMSBasicDocument"`

That `fileSource` makes the **native Liferay UI** show only an "upload from your computer" picker — no Documents and Media reference. But the **REST API still accepts a DLFileEntry id** referencing an existing document, as long as the user has VIEW permission on it. The empirical curl test that landed this:

```
shape sent              → result
{coverImage: <d.id>}    → 400 BAD_REQUEST
{coverImage: {id:d.id}} → 400 BAD_REQUEST
{coverImage: <file.id>} → 200 ✓
{coverImage: {id:f.id}} → 200 ✓
```

We send the raw `Number(file.id)` in `postBlog`. The "Object Entry id" (`d.id`) is misleading — the field stores the underlying file reference, not the wrapper Object's id.

### Connection error handling

`lrFetch` throws structured errors so callers can distinguish:

```js
err.kind === 'network'   // fetch itself rejected (offline, DNS, dev-server down)
err.kind === 'server'    // HTTP arrived with status outside 2xx
err.status, err.body     // populated only on 'server' kind
```

`liferayErrorMessage(err)` parses the JSON body and pulls a friendly summary (`title || message || detail`).

The two error surfaces:

- **Connection banner** (`#liferayError`, top of viewport): only shown for `network` errors and on boot-time preload failure (any kind, since with no spaces the prototype can't function). Auto-clears when a successful preload lands. User can dismiss; "Retry" button calls `preloadLiferaySpaces()`.
- **Inline form error** (`#formError`, in the content panel): for server-side validation failures during submit. Shows `liferayErrorMessage(err)` so the user sees Liferay's actual reason ("The value is invalid for object field coverImage" etc.) and can fix and retry. Form values are preserved.

### Activation gate

`liferayHealthy` is set to `true` only when `preloadLiferaySpaces()` succeeded with at least one space. `activationToggle()` checks it on every keypress in `idle`: if `false`, the mic doesn't activate, the banner re-shows (in case dismissed), `announce(s('errorLiferayConnection'), 'alert')` fires assertively for SR users, and a soft `fieldChange` sound plays. Mid-flow connection drops do NOT block — by then the user has work in progress and we trust them to decide whether to retry.

### finalizeSubmit awaits the API

`finalizeSubmit` is `async` and awaits the `api[submitApi]` call. If it returns `{ ok: false, ... }`:
- `kind === 'network'` — the api method already showed the connection banner; we just bail.
- `kind === 'server'` — call `showFormError(result.error)` to display Liferay's reason inline. The form state is NOT cleared; user fixes and retries.
- Success — proceed with the `submitted` mode + sentMsg cascade as before.

### No mock fallback

There used to be a `mockData` block in `config.{lang}.json` that fed the `api` getters when Liferay was unreachable. Removed once the integration was stable — having mocks meant connection failures looked like working data, hiding real problems. If you need offline UX work, set `liferay.enabled = false` in config and accept that submits and pickers return empty.

## Speech provider seam

To swap the recogniser (Deepgram, AssemblyAI, Google STT, Whisper, Azure, …) without changing the rest of the app:

1. Implement `createXProvider(opts)` returning the contract listed in *Speech recognition — provider seam*.
2. Register it in `createSpeechProvider(name, opts)`:
   ```js
   if (name === 'deepgram') return createDeepgramProvider(opts);
   ```
3. Set `appConfig.speech.provider = 'deepgram'` in config.json.
4. (For cloud APIs) point `opts.tokenEndpoint` or similar at a backend that mints a short-lived token. Don't hardcode keys in the browser.

Implementation notes for cloud streaming providers:
- Capture audio via `getUserMedia` + `MediaRecorder` (PCM 16 kHz mono if the API requires it).
- Stream chunks over WebSocket.
- On each transcript message: emit `onResult({ interim, final })` matching the contract.
- Handle reconnection internally; expose `onError` for unrecoverable cases.

Latency-wise, AudioContext FFT for the bars stays local and instant — only the transcript path changes.
